# 容量、性能与故障注入

## 容量模型

```powershell
npm run capacity:model -- --dau=1000 --records=1 --originalKiB=1500 --derivedKiB=500 --retentionDays=365 --exports=0.2 --peakFactor=4 --mediaSeconds=3
```

输出日记录数、日/保留存储、平均/峰值媒体 RPS、预估并发任务和月导出量。每月用真实匿名聚合数据更新参数，不用默认示例直接做扩容决策。

## 压测矩阵

- 登录、列表、记录写入、邀请公开读、媒体创建/完成/重试、回忆导出分开压测。
- 分别记录 p50/p95/p99、错误率、429 比例、CPU/内存、DB 连接/慢查询、Outbox/Job 积压和下游成本。
- 先基线，再逐级 1x/2x/4x 目标峰值，最后验证限流。高成本媒体和导出必须有独立配额。
- 只在 staging 使用受控测试账号/对象，禁止对生产做未审批压测。

## 故障注入

在 staging 分别使下游安全审核、抠图、COS 删除、订阅发送和 MySQL 连接超时，验证有界重试、指数退避、租约心跳、死信、告警和业务降级。注入时记录参数、预期、实际、恢复时间和清理结果。

## 架构决策阈值

- Runner 积压在容量调整后仍连续 15 分钟超过 5 分钟年龄，或 API CPU 与任务 CPU 相互挤压，才评审独立 Worker。
- DB 连接持续 > 80%、数据量/查询计划明确超过单库目标时，才评审升级、读写分离或归档。
- 不为预期规模提前引入 Redis/Kafka。任何扩容或并发参数调整都需压测证据、成本估算和回滚值。

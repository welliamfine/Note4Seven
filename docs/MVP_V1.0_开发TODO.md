## 1. 范围和可行性结论

当前 MVP 不是一个简单的展示型小程序，而是包含 58 个接口、23 张业务表、异步图片处理、两类审批、定时任务、订阅消息、数据回收和月度图片生成的完整产品。

建议团队配置：2 名前端（微信小程序）、2 名后端、1 名测试，产品/设计和运维按需参与。按该配置，完整 MVP 建议预留 11-14 周；若只有 1 名前端、1 名后端和兼职测试，建议按 18-24 周计划。总工作量粗估 150-200 人日，需另加 15%-20% 风险缓冲。最大不确定性是自动抠图质量/耗时、微信订阅消息、图片导出以及小程序审核。

推荐分三次交付：

1. Alpha（第 1-6 周）：登录 → 创建模块 → 上传/抠图 → 今日打卡 → 首页/日历/日期详情。
2. Beta（第 7-10 周）：邀请加入 → 成员管理 → 回应 → 补卡审批 → 通知/待办。
3. RC（第 11-14 周）：提醒 → 删除恢复 → 回忆/导出 → 全量埋点 → 压测、安全和提审。

明确不做：真实发现流、公开内容、评论私聊、视频、多图、4 人以上、数据导出文件、年度报告、会员、模块头像/图标、快速打卡和无照片提交。

## 8. 关键依赖关系

```text
架构/PoC
  → 工程基础、数据库、鉴权、幂等
  → 模块创建
  → 媒体 ready
  → 今日记录
  → 首页/月历/日期详情
  → 邀请加入/成员实例
  → 补卡/回应/通知
  → 日终快照
  → 月度回忆与导出
  → 全量回归、灰度和发布
```

可并行项：设计补稿可与 M1 并行；邀请/成员可在 M3 接口稳定后开发；回忆 UI 可先用固定数据开发，但真实验收依赖 Record、Reaction 和 DailySnapshot；埋点规范、测试基建和告警必须从 M1 开始，不应留到发布前集中补。

## 9. 每个任务的完成定义（DoD）

任务只有同时满足以下条件才能勾选：

- 需求和 Figma 状态明确，异常/空态/权限态已覆盖；
- API 契约、数据库迁移和错误码已同步；
- 服务端完成鉴权、幂等、事务/并发校验和审计（适用时）；
- 前端完成加载、失败、重试、系统返回、弱网和安全区处理；
- 单元/集成/E2E 测试通过，关键埋点可在测试环境查到；
- 无敏感内容进入日志或埋点；
- 代码评审通过，文档和 Runbook 已更新；
- 产品/设计/测试在 staging 按验收标准签字。

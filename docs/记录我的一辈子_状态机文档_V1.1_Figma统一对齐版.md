# 记录我的一辈子｜状态机文档 V1.1（Figma统一对齐版）

> 依据：PRD V6.4（纯照片打卡、无模块头像）  
> 文档目的：统一前端、后端、测试和产品对状态、转换条件、权限、并发和副作用的理解。

---

## 0. 对齐说明

- Figma已展示的页面和弹层形态优先；
- 业务持久化状态仍由服务端维护；
- 高位编辑面板、照片来源面板、日期详情面板属于前端UI状态；
- 未来日期打开只读日期面板；
- 双人日历采用上下居中固定槽位；
- 邀请和成员管理中的叶子是固定装饰，不存在业务状态；
- 备注统一称为 `remark`。

---

## 1. 状态机使用原则

1. 所有关键状态由服务端维护，前端不得自行推断最终业务状态。
2. 前端可以维护加载、动画和弹层等临时 UI 状态，但不得替代持久化状态。
3. 状态转换必须由明确事件触发，并校验操作者权限和业务时间。
4. 写操作必须支持 `clientRequestId` 幂等。
5. 并发审批使用原子条件更新或数据库行锁。
6. 模块状态、成员状态和业务日期是所有子状态机的上层守卫条件。
7. 所有业务日期按 `Asia/Shanghai` 计算。
8. 模块进入 `pending_delete` 后，所有新增、编辑、审批、邀请和提醒状态机停止正常推进。
9. 本版本不存在快速打卡、无照片记录或模块头像状态。

---

## 2. 状态优先级

当多个条件同时存在时，按以下优先级决定页面和操作权限：

```text
模块 deleted
> 模块 pending_delete
> 用户非活跃成员
> 日期不可操作
> 记录/审批具体状态
> 媒体处理状态
> 页面临时状态
```

示例：

- 即使媒体已经 ready，只要模块进入 pending_delete，也不得保存记录；
- 即使补卡审批仍显示 pending，只要申请人已退出，审批应转 cancelled；
- 即使邀请 Token 尚未到 expireAt，只要模块满员或进入回收期，申请按钮不可用。

# 3. 模块生命周期状态机

## 3.1 状态定义

| 状态 | 含义 | 是否可查看 | 是否可写 |
|---|---|---:|---:|
| `active` | 正常使用 | 是 | 是 |
| `pending_delete` | 7天回收期 | 创建者可进入恢复页；普通成员看删除提示 | 否 |
| `deleted` | 永久删除完成 | 否 | 否 |

## 3.2 转换图

```text
active
  └─ creator_delete
       ↓
pending_delete
  ├─ creator_restore → active
  └─ recycle_expired → deleted
```

## 3.3 转换矩阵

| 当前状态 | 事件 | 守卫条件 | 下一状态 | 主要副作用 |
|---|---|---|---|---|
| active | `creator_delete` | 操作者为创建者；输入模块名正确 | pending_delete | 设置 deletedAt/recycleExpireAt；取消审批和加入申请；失效 Token；停止提醒；通知所有成员 |
| pending_delete | `creator_restore` | 操作者仍为创建者；未超过回收期 | active | 恢复访问；重建提醒任务；旧审批、旧申请和旧 Token 不恢复 |
| pending_delete | `recycle_expired` | 服务端时间达到 recycleExpireAt | deleted | 异步删除数据库内容、媒体、缓存和派生资源 |
| active | `delete_by_non_creator` | 非创建者 | active | 拒绝并记录审计 |
| deleted | 任意业务事件 | - | deleted | 返回 MODULE_DELETED |

## 3.4 进入回收期的级联状态

模块变为 `pending_delete` 时：

- MakeupApproval pending → cancelled；
- 对应 Record pending → cancelled；
- JoinApplication pending → cancelled；
- InviteToken active → invalid_module；
- ReminderSubscription 保留配置但暂停执行；
- Notification 动作卡变为 resolved/expired；
- ModuleInboxItem 未处理项变为 resolved；
- 当天不新增共同完成统计。

# 4. 模块模式状态机

## 4.1 状态

- `solo`
- `group`

## 4.2 转换

```text
solo
  └─ first_new_member_approved → group

group
  └─ 永久保持 group
```

| 当前状态 | 事件 | 下一状态 | 说明 |
|---|---|---|---|
| solo | 第一名新成员加入成功 | group | 设置 groupActivatedAt |

# 5. 成员关系状态机

## 5.1 状态定义

| 状态 | 存储位置 | 含义 |
|---|---|---|
| `not_joined` | 派生状态 | 当前没有 active 成员实例 |
| `applying` | JoinApplication=pending | 正在申请 |
| `active` | ModuleMember=active | 可访问和记录 |
| `exited` | ModuleMember=exited | 主动退出 |
| `removed` | ModuleMember=removed | 被创建者移除 |

## 5.2 转换图

```text
not_joined
  └─ submit_join_application → applying

applying
  ├─ approve → active（创建新 memberInstanceId）
  ├─ reject → not_joined
  ├─ expire → not_joined
  └─ cancel → not_joined

active
  ├─ self_exit → exited
  └─ creator_remove → removed

exited / removed
  └─ submit_new_application → applying
       └─ approve → active（新的 memberInstanceId）
```

## 5.3 转换矩阵

| 当前状态 | 事件 | 守卫条件 | 下一状态 | 副作用 |
|---|---|---|---|---|
| not_joined | submit application | Token有效；模块active；人数<4；无pending申请 | applying | 创建JoinApplication；通知创建者 |
| applying | approve | 操作者为当前创建者；申请pending；人数<4 | active | 创建新Member；分配joinSequence；可能solo→group |
| applying | reject | 当前创建者；申请pending | not_joined | 申请rejected；设置24小时再次申请时间 |
| applying | expire | 7天未处理 | not_joined | 申请expired；通知申请人 |
| applying | cancel | 模块删除、用户已加入或系统取消 | not_joined/active | 申请cancelled |
| active | self_exit | 普通成员；模块active | exited | 失去权限；取消本人待审批补卡；历史匿名 |
| active | creator_remove | 操作者为创建者；目标为普通成员 | removed | 失去权限；历史匿名；释放名额 |
| exited/removed | reapply | 满足新申请条件 | applying | 创建全新申请 |
| active creator | self_exit | 未转让且未删除模块 | active | 拒绝 |

## 5.4 重新加入规则

重新加入：

- 不恢复旧 ModuleMember；
- 新建 `memberInstanceId`；
- 新建 `joinSequence`；
- 排在当前成员末尾；
- 旧记录继续显示为“已退出成员”；
- 新身份不能编辑旧身份的记录。

# 6. 邀请 Token 状态机

## 6.1 状态

- `active`
- `revoked`
- `expired`
- `invalid_module`

## 6.2 转换图

```text
active
  ├─ creator_revoke → revoked
  ├─ expire_at_reached → expired
  ├─ module_pending_delete → invalid_module
  └─ module_deleted → invalid_module
```

模块满员时 Token 可保持数据库 active，但在运行时视为不可申请；建议异步更新为 invalid_module 或在返回中给出 `module_full` 派生状态。

## 6.3 运行时有效条件

Token 可用于打开和申请必须同时满足：

```text
token.status = active
AND now < expireAt
AND module.status = active
AND activeMemberCount < 4
```

Token 过期不影响已经成功创建的 JoinApplication。

# 7. 加入申请状态机

## 7.1 状态

- `pending`
- `approved`
- `rejected`
- `expired`
- `cancelled`

## 7.2 转换图

```text
pending
  ├─ creator_approve → approved
  ├─ creator_reject → rejected
  ├─ seven_days_elapsed → expired
  └─ system_cancel → cancelled
```

`approved` 后创建 ModuleMember，页面派生为 `active_member`，不建议把 `active_member` 作为 JoinApplication 的数据库状态。

## 7.3 转换矩阵

| 当前状态 | 事件 | 守卫条件 | 下一状态 | 返回 |
|---|---|---|---|---|
| pending | approve | 创建者；模块active；人数<4；申请人非active成员 | approved | 返回新memberInstanceId |
| pending | reject | 创建者；模块active | rejected | 设置reapplyAllowedAt |
| pending | expire | now>=expireAt | expired | 卡片只读 |
| pending | module delete | module pending_delete | cancelled | 目标失效 |
| pending | applicant already active | 用户通过其他申请加入 | cancelled | 进入模块 |
| 非pending | approve/reject | - | 原状态 | JOIN_APPLICATION_ALREADY_RESOLVED |

## 7.4 并发

审批 SQL 必须包含 `status='pending'`。若两个客户端同时操作，只有一个成功；另一个刷新卡片并提示“申请已处理”。

# 8. 媒体上传与抠图状态机

## 8.1 状态拆分

媒体总状态：

```text
created → uploading → uploaded → processing → ready
```

失败或放弃分支：

```text
uploading → failed
uploaded/processing → failed
created/uploading/uploaded/processing → abandoned
ready → pending_delete → deleted
```

抠图子状态：

```text
not_started → queued → processing → succeeded
                            └→ failed
```

## 8.2 转换矩阵

| 当前状态 | 事件 | 守卫条件 | 下一状态 | UI |
|---|---|---|---|---|
| created | upload_start | 文件格式/大小预校验通过 | uploading | 显示上传进度 |
| uploading | upload_success | 对象存储成功 | uploaded | 开始服务端处理 |
| uploading | upload_fail | 网络或存储失败 | failed | 重试/替换 |
| uploaded | enqueue_cutout | 文件可读取 | processing | 显示抠图中 |
| processing | cutout_success | 贴纸和缩略图均生成 | ready | 展示预览，开放保存 |
| processing | cutout_fail | 服务失败/超时 | failed | 仅重试或替换 |
| 任意未ready | replace_photo | 用户选择新照片 | abandoned | 创建新Media |
| ready | record_saved | 关联正式Record | ready | 成为业务素材 |
| ready | replaced_and_new_saved | 旧媒体失去引用 | pending_delete | 异步清理 |

## 8.3 保存守卫

正式 Record 只能在以下条件同时满足时创建或更新：

```text
media.status = ready
cutoutStatus = succeeded
originalFileKey存在
stickerFileKey存在
stickerThumbnailFileKey存在
```

前端保存按钮的启用状态只是视觉提示，服务端必须重复校验。

# 9. 普通今日记录状态机

## 9.1 持久化状态

- `active`
- `locked`
- `deleted`

媒体处理发生在 Record 创建前，因此 `uploading/processing` 是编辑器和 MediaAsset 状态，不是正式 Record 状态。

## 9.2 转换图

```text
无记录
  └─ save_ready_photo → active

active
  ├─ edit_remark_or_photo → active（版本更新）
  ├─ delete_today → deleted
  └─ cross_midnight → locked

deleted
  └─ new_record_today → 新的 Record(active)

locked
  └─ 只读终态
```

## 9.3 转换矩阵

| 当前状态 | 事件 | 守卫条件 | 下一状态 | 副作用 |
|---|---|---|---|---|
| 无记录 | save | D0；模块active；成员active；Media ready | active | 设置firstEffectiveAt；刷新首页贴纸堆 |
| active | edit | 本人；仍为D0；新Media ready或只改备注 | active | updatedAt/version变化；firstEffectiveAt不变 |
| active | delete | 本人；D0 | deleted | 贴纸消失；回应停止展示；写审计 |
| active | midnight lock | recordDate < currentDate | locked | lockedAt写入 |
| deleted | re-record | 仍为D0；无其他有效记录 | 新active记录 | 新recordId、新firstEffectiveAt |
| locked | edit/delete | - | locked | 返回 RECORD_LOCKED |

## 9.4 首页贴纸堆派生状态

首页卡片读取当日 active/locked 正式记录：

- 按 `firstEffectiveAt ASC`；
- 取最后 4 条；
- 最右侧为最新、层级最高；
- 新增后旧贴纸向左移动；
- 编辑不改变位置；
- 删除后剩余贴纸重新排布；
- 删除后重新打卡作为最新贴纸。

# 10. 补卡记录和审批状态机

## 10.1 单人模式

```text
无记录
  └─ submit_makeup_ready_photo → locked
```

不创建待审批状态，提交成功立即生效并锁定。

## 10.2 多人模式

Record：

```text
无记录
  └─ submit_makeup → pending
       ├─ approval_approved → locked
       ├─ approval_rejected → rejected
       ├─ approval_expired → expired
       └─ approval_cancelled → cancelled
```

MakeupApproval：

```text
pending
  ├─ first_approve → approved
  ├─ first_reject → rejected
  ├─ 24h_elapsed → expired
  └─ system_cancel → cancelled
```

## 10.3 审批矩阵

| 当前审批状态 | 事件 | 守卫条件 | 下一状态 | Record状态 |
|---|---|---|---|---|
| pending | approve | 操作者为其他有资格active成员；未过期 | approved | locked |
| pending | reject | 同上 | rejected | rejected |
| pending | expire | now>=expireAt | expired | expired |
| pending | applicant_exit | 申请成员不再active | cancelled | cancelled |
| pending | module_delete | 模块pending_delete | cancelled | cancelled |
| pending | approver_exit | 当前操作者失去资格 | pending | 不变，其他人可审批 |
| 非pending | approve/reject | - | 原状态 | 原状态 |

## 10.4 特殊审批人规则

多人模块只剩申请人一名活跃成员时：

- 申请人不是创建者：由创建者审批；
- 申请人就是创建者且无其他活跃成员：补卡直接通过并锁定。

## 10.5 重新申请

rejected/expired/cancelled 记录不恢复。满足 D-1 至 D-3 范围时创建：

- 新 recordId；
- 新 approvalId；
- 新 clientRequestId；
- attemptNumber + 1。

```text
无回应
```

# 12. 通知状态机

## 12.1 阅读状态

```text
unread → read
```

阅读不可逆。业务目标失效不自动等于已读。

## 12.2 可执行动作状态

```text
actionable
  ├─ user_click → processing
  │    ├─ success → resolved
  │    └─ request_fail → actionable
  ├─ target_already_resolved → resolved
  └─ target_expired → expired
```

## 12.3 加入审批通知

| 状态 | UI |
|---|---|
| actionable | 展示同意/拒绝 |
| processing | 两个按钮禁用，显示处理中 |
| resolved | 展示处理结果 |
| expired | 只读“申请已过期/目标失效” |

通知表动作状态不是事实源；每次操作必须读取 JoinApplication。

# 13. 模块内待办状态机

模块内待办项状态：

- `unread`
- `read`
- `resolved`
- `expired`

```text
unread → read
unread/read → resolved
unread/read → expired
```

适用类型：

- 待审批补卡；
- 本人补卡结果；
- 成员变更；
- 模块状态变化；
- 新回应。

同一记录多个回应可使用 dedupeKey 合并为一项，并更新最后发生时间和数量。

# 14. 提醒状态机

## 14.1 配置状态

```text
disabled
  └─ user_enable → requesting_permission

requesting_permission
  ├─ authorized → enabled_external
  └─ denied → enabled_in_app_only

enabled_external
  ├─ user_disable → disabled
  ├─ authorization_exhausted → enabled_in_app_only
  └─ provider_unavailable → enabled_in_app_only

enabled_in_app_only
  ├─ user_reauthorize → enabled_external
  └─ user_disable → disabled
```

数据库可使用 `enabled + subscriptionStatus` 组合表达。

## 14.2 单次发送状态

```text
scheduled
  ├─ already_recorded → skipped
  ├─ member_inactive → skipped
  ├─ module_not_active → skipped
  ├─ daily_limit_reached → skipped
  ├─ provider_success → sent
  └─ provider_fail → failed
```

失败不进行高频补偿，不影响打卡主流程。

# 15. 共同完成状态机

共同完成不是手工操作状态，而是每日快照计算结果。

## 15.1 派生状态

- `not_applicable`：日终活跃成员少于2，或模块当天进入回收期；
- `incomplete`：存在未完成成员；
- `completed`：所有应完成成员均有有效记录。

## 15.2 计算

日终：

```text
collect end-of-day active members
→ save member snapshot
→ count effective records
→ calculate isAllCompleted
```

补卡通过：

```text
locked makeup record created
→ load historical member snapshot
→ recalculate completedMemberCount
→ update incomplete/completed
```

成员后续退出或重新加入不得改变已保存的历史成员集合。


# 17A. Figma界面临时状态机

本节状态只存在于小程序页面实例中，不直接写数据库，但必须与业务状态同步。

## 17A.1 日期详情面板

```text
closed
  └─ date_click → opening
       └─ animation_end → open
            ├─ close_x/drag/mask/system_back → closing → closed
            ├─ record_today → closing → record_editor_opening
            ├─ edit_today → closing → record_editor_opening
            └─ apply_makeup → closing → makeup_editor
```

未来日期：

```text
closed → compact_future_open
compact_future_open → close → closed
```

`compact_future_open` 不允许转换到记录编辑或补卡。

## 17A.2 打卡编辑高位面板

```text
closed
  └─ open_create/open_edit → opening
       └─ open
            ├─ photo_area_click → photo_source_opening
            ├─ submit → submitting
            ├─ delete_click(edit only) → closing → delete_confirm
            └─ close_attempt → dirty_check
```

关闭判断：

```text
dirty_check
  ├─ clean → closing → closed
  ├─ continue_edit → open
  └─ discard → abandon_unlinked_media → closing → closed
```

标题派生：

- create：记录今天；
- edit：编辑今天；
- makeup：补记 M月D日。

底部按钮均为“完成！”，但只有Media ready时可提交。

## 17A.3 照片来源操作面板

```text
closed
  └─ add_or_replace → opening → open
       ├─ camera → close_and_launch_camera
       ├─ gallery → close_and_launch_gallery
       └─ drag/mask/system_back → closing → closed
```

关闭后必须恢复底层编辑面板，包括remark、旧照片和媒体处理进度。

## 17A.4 编辑器照片视觉状态

```text
empty
  └─ select_photo → compressing
       → uploading
       → processing
       → ready
```

分支：

```text
compressing/uploading/processing → failed
failed → retry | replace
ready → replace → pending_new_media
pending_new_media → new_ready → ready
```

编辑旧记录时，新媒体保存成功前旧贴纸继续作为正式数据。

# 18. 跨状态机级联规则

## 18.1 成员退出/移除

触发：

- ModuleMember active → exited/removed；
- 取消其 pending MakeupApproval；
- 其 pending Record → cancelled；
- 失效其提醒执行资格；
- 历史 Record 和 Reaction 保留；
- API 展示为“已退出成员”；
- 释放模块名额；
- 刷新当前成员状态栏和未来日历槽位。

## 18.2 加入通过

触发：

- JoinApplication pending → approved；
- 新建 ModuleMember active；
- 分配新 joinSequence；
- Module activeMemberCount + 1；
- solo 首次变 group；
- 首页、成员栏、成员管理和日历刷新；
- 生成通知和待办。

## 18.3 正式记录生效

触发：

- Record → active/locked；
- 首页贴纸堆刷新；
- 月历贴纸刷新；
- Module.lastActivityAt更新；
- 共同完成快照新增或重算；
- 回忆卡标记 stale；
- 取消当天本人提醒任务。

## 18.4 今日记录删除

触发：

- Record active → deleted；
- 首页贴纸移除；
- 日历贴纸移除；
- 回应停止展示；
- 当日共同完成重新计算；
- 回忆卡标记 stale；
- 今日按钮变“记录今日”。

## 18.5 模块进入回收期

优先级最高，覆盖所有子流程：

- 禁止新 Record；
- 禁止编辑/删除业务内容；
- 取消补卡和加入申请；
- Token 失效；
- 提醒停止；
- 通知动作变只读；
- 创建者只可恢复。

# 19. 失败和重试策略

## 19.1 客户端超时但服务端成功

客户端使用相同 `clientRequestId` 重试：

- 服务端返回第一次成功结果；
- 不创建重复 Record、申请或成员实例；
- 前端拉取最新详情刷新。

## 19.2 媒体失败

- 上传失败：允许同 mediaId 重传或创建新 mediaId；
- 抠图失败：允许重试任务；
- 用户替换照片：旧媒体 abandoned；
- 未 ready 的媒体不能创建 Record。

## 19.3 并发冲突

统一返回可识别业务码：

- `RECORD_ALREADY_EXISTS`
- `APPLICATION_ALREADY_RESOLVED`
- `APPROVAL_ALREADY_RESOLVED`
- `MODULE_MEMBER_LIMIT_REACHED`
- `VERSION_CONFLICT`
- `MODULE_PENDING_DELETE`

前端应刷新，而不是本地强行推进状态。

# 20. 定时状态转换

| 任务 | 状态转换 |
|---|---|
| 每日零点锁定 | Record active → locked |
| 补卡审批超时 | MakeupApproval pending → expired；Record pending → expired |
| 加入申请超时 | JoinApplication pending → expired |
| 邀请到期 | InviteToken active → expired |
| 回收期到期 | Module pending_delete → deleted |
| 日终计算 | DailySnapshot → incomplete/completed/not_applicable |
| 媒体孤儿清理 | Media abandoned/failed → pending_delete → deleted |
| 提醒扫描 | scheduled → sent/skipped/failed |

所有定时任务必须幂等，可重复执行。

# 21. 状态机接口返回建议

所有涉及状态的接口建议返回：

```json
{
  "status": "active",
  "availableActions": [
    "edit",
    "delete"
  ],
  "statusReason": null,
  "version": 3,
  "serverTime": "2026-07-15T12:00:00+08:00"
}
```

前端优先使用 `availableActions` 控制入口，同时仍显示明确状态文案。服务端执行时再次鉴权和校验。

# 22. 状态机验收用例

## 22.1 模块

- [ ] active 模块仅创建者可进入 pending_delete；
- [ ] pending_delete 内所有业务写操作失败；
- [ ] 7天内创建者可恢复；
- [ ] 恢复后旧 Token 和已取消申请不恢复；
- [ ] 到期后无法恢复。

## 22.2 成员

- [ ] 单模块最多4名active成员；
- [ ] 退出后立即失去访问权限；
- [ ] 重新加入创建新memberInstanceId；
- [ ] 新joinSequence排在末尾；
- [ ] 创建者不能直接退出；
- [ ] 转让后只有一个创建者。

## 22.3 媒体和记录

- [ ] 抠图未成功时保存按钮和接口均不可用；
- [ ] 今日记录可编辑、删除；
- [ ] 编辑不改变firstEffectiveAt；
- [ ] 跨日后自动locked；
- [ ] 删除后可重新打卡并生成新排序时间；
- [ ] 一人一天不能同时有两条有效记录。

## 22.4 补卡

- [ ] 仅D-1至D-3可申请；
- [ ] 单人直接locked；
- [ ] 多人进入pending；
- [ ] 首个有效审批决定结果；
- [ ] 申请人不能审批自己；
- [ ] 24小时后自动expired；
- [ ] 被拒后在有效日期内可创建全新申请；
- [ ] 退出或模块删除时pending申请cancelled。

## 22.5 邀请加入

- [ ] Token 24小时过期；
- [ ] Token过期不影响已提交申请；
- [ ] 被拒后24小时不可再次申请；
- [ ] 申请7天后过期；
- [ ] 审批时人数满则同意失败；
- [ ] 并发审批只有一个结果生效。

## 22.6 回应和通知

- [ ] 一人一条记录最多一个有效回应；
- [ ] 更换表情不新增第二行；
- [ ] 退出后回应保留并匿名；
- [ ] 加入申请卡 processing 时按钮禁用；
- [ ] 已处理卡片刷新为resolved；
- [ ] 全局未读与模块待办分别统计。

## 22.7 日历

- [ ] 有贴纸日期隐藏日期数字；
- [ ] 未记录槽位保持为空；
- [ ] 多人贴纸按joinSequence固定；
- [ ] 3人时第一行2个、第二行1个居中；
- [ ] 退出成员历史身份匿名；
- [ ] 补卡通过后目标日期和共同完成状态重新计算。

# 23. Figma一致性验收补充

- [ ] 未来日期点击后进入compact_future_open，而非Toast；
- [ ] create与edit共用同一高位编辑面板；
- [ ] 照片来源面板只含拍照和从相册选择；
- [ ] 二级照片来源面板关闭后恢复编辑器状态；
- [ ] 双人成员槽位严格为top_center、bottom_center；
- [ ] 三人槽位严格为top_left、top_right、bottom_center；
- [ ] 叶子装饰不进入任何状态机；
- [ ] editorMode=create时标题为记录今天，edit时为编辑今天；
- [ ] 完成按钮在media ready前不可触发Record状态转换。

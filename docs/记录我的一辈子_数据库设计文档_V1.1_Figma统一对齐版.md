# 记录我的一辈子｜数据库设计文档 V1.1（Figma统一对齐版）

> 依据：PRD V6.4（纯照片打卡、无模块头像）  
> 配套文档：接口文档 V1.1、埋点文档 V1.1、状态机 V1.1  
> 文档目的：明确研发阶段的数据实体、字段、约束、索引、事务、生命周期和数据清理规则。

---

## 0. 版本对齐说明

V1.1在V1.0完整数据模型基础上统一以下规则：

- Figma已展示的页面结构优先；
- 新增/编辑共用高位底部编辑面板，但编辑器临时状态不写入业务数据库；
- 备注字段统一为 `remark`；
- 日历双人布局为上、下居中；三人为上二、下居中；四人为2×2；
- `layout_slot` 是按活跃成员数量和 `join_sequence` 计算的响应字段，默认不作为成员永久属性存储；
- 邀请页和成员管理页的叶子是固定客户端装饰，不建立字段或资源表；
- Module不得新增头像、图标、记录类型或装饰字段。

## 1. 设计范围

本数据库设计覆盖以下业务：

- 微信登录与用户资料；
- 记录模块创建、置顶和删除回收；
- 单人/多人模块；
- 单模块最多 4 名活跃成员；
- 照片上传、自动抠图、贴纸和缩略图生成；
- 今日打卡、编辑、删除；
- D-1 至 D-3 补卡和多人审批；
- 贴纸日历、日期详情和首页贴纸堆；
- 表情回应；
- 邀请 Token、加入申请和成员管理；
- 创建者转让、成员退出和移除；
- 模块内待办、全局通知；
- 个人提醒和微信订阅消息；
- 共同完成快照；
- 月度回忆卡；
- 审计日志、幂等和异步事件。

本设计不包含模块头像、模块图标、快速打卡类型、默认状态图标或无照片记录。

## 2. 推荐技术基线

本文是逻辑数据库设计，字段类型以 MySQL 8.0 兼容写法表示。使用 PostgreSQL 时可将 `BIGINT` 主键替换为 UUID/ULID，并使用部分唯一索引实现有效记录约束。

建议：

- 主数据库：MySQL 8.0 或 PostgreSQL 15；
- 缓存：Redis；
- 对象存储：云对象存储；
- 异步任务：消息队列或可靠任务表；
- 字符集：`utf8mb4`；
- 业务时区：`Asia/Shanghai`；
- 数据库 `DATETIME`、数据库会话和接口时间统一使用 `Asia/Shanghai`（`+08:00`）；
- `record_date` 使用业务日期 `DATE`，不得由客户端本地时区直接推导；
- 金额字段不存在，不使用浮点数参与业务判断；
- 所有写操作支持 `client_request_id` 幂等。

## 3. 命名和公共字段规范

### 3.1 命名

- 数据库表和字段使用 `snake_case`；
- 主键使用 `<entity>_id`；
- 外键字段名称与目标主键一致；
- 时间字段统一以 `_at` 结尾；
- 布尔字段统一以 `is_` 或 `has_` 开头；
- 状态字段使用字符串枚举，不使用不可读的数字魔法值。

### 3.2 ID

推荐使用以下任一方案：

1. `BIGINT UNSIGNED` 雪花 ID；
2. 26 位 ULID；
3. UUIDv7。

要求：

- 全局唯一；
- 不暴露自增规模；
- 可按创建时间大致排序；
- 客户端不得自行生成核心业务实体 ID，`client_request_id` 除外。

### 3.3 公共时间字段

业务表通常包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `created_at` | DATETIME(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 最后更新时间 |
| `deleted_at` | DATETIME(3) NULL | 软删除时间，仅适用于需要留痕的实体 |
| `version` | INT UNSIGNED | 乐观锁版本号 |

### 3.4 软删除原则

- 模块在 7 天回收期内使用状态控制，不立即物理删除；
- 今日记录删除后保留记录行，用于审计和幂等判断；
- 媒体文件先标记待清理，异步删除对象存储内容；
- 回收期到期后允许物理删除模块内容；
- 审计日志按安全策略单独保留。

### 4.1 日历布局派生规则

日历槽位不属于模块或成员的可编辑业务属性，由查询服务依据当前成员集合计算：

| 活跃成员数 | joinSequence顺序 | layoutSlot |
|---:|---|---|
| 1 | 1 | `center` |
| 2 | 1、2 | `top_center`、`bottom_center` |
| 3 | 1、2、3 | `top_left`、`top_right`、`bottom_center` |
| 4 | 1、2、3、4 | `top_left`、`top_right`、`bottom_left`、`bottom_right` |

数据保存原则：

- `module_member.join_sequence` 是事实字段；
- `record.join_sequence_snapshot` 保存记录发生时顺序；
- `daily_module_snapshot_member` 保存历史成员集合；
- `layout_slot` 默认在接口聚合层派生，不写入Module或ModuleMember；
- 如为性能建立月历聚合缓存，缓存中可存 `layout_slot`，但必须可由事实数据重建；
- 首页贴纸不使用该布局，按Record.first_effective_at排序。

# 6. 核心业务表

## 6.1 `user`

用户账号表。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|---|---|---:|---|---|
| `user_id` | BIGINT UNSIGNED | 否 | - | 主键 |
| `open_id` | VARCHAR(64) | 否 | - | 微信 OpenID |
| `union_id` | VARCHAR(64) | 是 | NULL | 微信 UnionID |
| `nickname` | VARCHAR(64) | 否 | - | 当前昵称 |
| `avatar_url` | VARCHAR(512) | 是 | NULL | 当前头像 |
| `status` | VARCHAR(20) | 否 | `active` | 用户状态 |
| `last_login_at` | DATETIME(3) | 是 | NULL | 最近登录 |
| `created_at` | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | 创建时间 |
| `updated_at` | DATETIME(3) | 否 | CURRENT_TIMESTAMP(3) | 更新时间 |
| `version` | INT UNSIGNED | 否 | 0 | 乐观锁 |

约束与索引：

- PK：`user_id`
- UNIQUE：`open_id`
- INDEX：`union_id`
- INDEX：`status, updated_at`

说明：

- 历史记录不能直接读取用户当前昵称和头像；
- 历史展示使用 Record/Reaction 快照，并在退出成员场景由服务端匿名化。

## 6.5 `module_member`

成员关系实例表。用户退出后重新加入必须创建新实例。

| 字段 | 类型 | 可空 | 说明 |
|---|---|---:|---|
| `member_instance_id` | BIGINT UNSIGNED | 否 | 主键 |
| `module_id` | BIGINT UNSIGNED | 否 | 模块 |
| `user_id` | BIGINT UNSIGNED | 否 | 用户 |
| `role` | VARCHAR(16) | 否 | `creator/member` |
| `status` | VARCHAR(16) | 否 | `active/exited/removed` |
| `join_sequence` | INT UNSIGNED | 否 | 加入顺序，永久不复用 |
| `joined_at` | DATETIME(3) | 否 | 加入时间 |
| `left_at` | DATETIME(3) | 是 | 离开时间 |
| `leave_reason` | VARCHAR(32) | 是 | `self_exit/removed/module_deleted` 等 |
| `nickname_snapshot` | VARCHAR(64) | 否 | 加入时昵称快照 |
| `avatar_snapshot` | VARCHAR(512) | 是 | 加入时头像快照 |
| `created_at` | DATETIME(3) | 否 | 创建时间 |
| `updated_at` | DATETIME(3) | 否 | 更新时间 |
| `version` | INT UNSIGNED | 否 | 乐观锁 |

约束与索引：

- PK：`member_instance_id`
- UNIQUE：`module_id, join_sequence`
- INDEX：`module_id, status, join_sequence`
- INDEX：`user_id, status`
- INDEX：`module_id, user_id, status`
- 同一模块同一用户最多一个 `active` 成员实例。

MySQL 可使用生成列实现“一个活跃实例”唯一约束：

```sql
active_user_key =
CASE WHEN status = 'active'
THEN CONCAT(module_id, ':', user_id)
ELSE NULL END
```

并对 `active_user_key` 建唯一索引。

说明：

- 历史贴纸槽位使用 `join_sequence_snapshot`；
- 当前成员状态栏按当前活跃成员 `join_sequence` 排序；
- 被移除或退出的旧实例永不恢复为 active。

- INDEX：`module_id, record_date, first_effective_at`
- INDEX：`media_id`
- INDEX：`status, updated_at`

### 一人一天一条有效记录约束

有效占位状态包括：

- `pending`
- `active`
- `locked`

MySQL 推荐生成列：

```sql
effective_daily_key =
CASE
  WHEN status IN ('pending', 'active', 'locked')
  THEN CONCAT(module_id, ':', member_instance_id, ':', DATE_FORMAT(record_date, '%Y-%m-%d'))
  ELSE NULL
END
```

对 `effective_daily_key` 建唯一索引。

这样可以：

- 阻止同一成员同日重复正式记录；
- 今日删除后允许创建新 Record；
- 补卡被拒/取消/过期后允许创建新的申请；
- 保留全部历史申请记录。

记录成立条件：

- `media_asset.status = ready`；
- `media_asset.cutout_status = succeeded`；
- 模块为 active；
- 成员为 active；
- 普通打卡日期为 D0；
- 补卡日期为 D-1 至 D-3。

首页贴纸堆：

- 查询当天 `active/locked` 记录；
- 按 `first_effective_at ASC`；
- 最多返回最新 4 条；
- 编辑不改变 `first_effective_at`；
- 删除后重新打卡生成新记录和新排序时间。

# 7. 关键事务设计

## 7.1 创建模块

单事务：

1. 插入 Module；
2. 插入创建者 ModuleMember，`join_sequence=1`；
3. 回写 Module 的 creator member ID；
4. 插入 UserModulePreference；
5. 写 AuditLog；
6. 写 OutboxEvent。

失败全部回滚。

## 7.2 今日打卡

前置条件：

- Module active；
- ModuleMember active；
- 日期为 D0；
- MediaAsset ready；
- 无有效日记录。

事务：

1. 创建 Record，状态 active；
2. 写 `first_effective_at`；
3. 关联 media；
4. 插入 RecordRevision；
5. 更新 Module.last_activity_at；
6. 写 OutboxEvent；
7. 提交后刷新首页、日历、统计。

## 7.3 编辑今日记录

- 锁定 Record；
- 校验 status=active 且 record_date=D0；
- 若换图，校验新 MediaAsset ready；
- 保持 `first_effective_at` 不变；
- 更新 Record；
- 插入 RecordRevision；
- 旧媒体进入待清理；
- 写 OutboxEvent。

## 7.4 删除今日记录

- 锁定 Record；
- 校验本人、D0、status=active；
- 更新 status=deleted；
- 取消展示相关 Reaction；
- 写 AuditLog 和 OutboxEvent；
- 不物理删除记录行。

## 7.5 补卡申请

单人模式：

- 创建 Record 为 locked；
- `source=makeup`；
- 设置 approved_at/locked_at；
- 不创建 pending 审批。

多人模式：

- 创建 Record 为 pending；
- 创建 MakeupApproval 为 pending；
- 生成模块内待办；
- 写 OutboxEvent。

## 7.6 补卡审批

使用行锁或条件更新，首个有效操作决定结果。

通过：

- approval pending → approved；
- record pending → locked；
- 设置 approved_at、locked_at、first_effective_at；
- 更新目标日期快照；
- 生成结果通知。

拒绝：

- approval pending → rejected；
- record pending → rejected；
- 生成结果通知。

## 7.7 加入审批

必须锁定 Module 和 JoinApplication，重新校验：

- 模块 active；
- 申请 pending；
- 创建者权限；
- 人数未满；
- 用户不是活跃成员。

通过后创建新成员实例并更新模块人数。

## 7.8 转让创建者

单事务：

- 锁定 Module；
- 锁定原创建者和目标成员；
- 校验二者均 active；
- 原创建者 role → member；
- 目标成员 role → creator；
- 更新 Module creator 字段；
- 写通知、审计、Outbox。

任何时刻只能存在一个 active creator。

# 8. 数据一致性和并发

## 8.1 乐观锁

以下表建议使用 `version`：

- module；
- module_member；
- record；
- makeup_approval；
- join_application；
- reaction；
- reminder_subscription。

更新条件：

```sql
WHERE id = ? AND version = ?
```

成功后 `version = version + 1`。

## 8.2 人数上限

审批加入时必须锁 Module 行，并校验 `active_member_count < member_limit`。不得只依赖加入申请创建时的检查。

## 8.3 首个审批生效

补卡审批、加入审批均采用条件更新。前端收到“已处理”后重新拉取状态。

## 8.4 跨日

服务端每次写 Record 都重新计算 `record_date` 权限。页面在 23:59 打开、00:00 提交时按提交时服务端日期处理。

## 8.5 缓存

缓存只用于读取：

- 首页模块列表；
- 模块详情；
- 月历；
- 未读数；
- 回忆卡。

权限、成员数、审批和唯一记录判断必须命中主数据库，不得只依赖缓存。

# 9. 数据生命周期

## 9.1 图片

- 原图、缩略图、贴纸和贴纸缩略图独立对象 Key；
- 数据库只存 Key，不存永久公开 URL；
- 下载 URL 使用短期签名；
- 无权限用户不得获得原图 URL；
- abandoned 媒体 24 小时后清理；
- 模块永久删除时清理全部媒体；
- 清理任务必须幂等。

## 9.2 模块回收

`pending_delete` 后保留 7 个自然日：

- 禁止新增、编辑、审批、邀请和提醒；
- 可由创建者恢复；
- 到期异步物理删除关联内容。

## 9.3 通知

建议在线通知保留至少 180 天；超过期限可归档或清理。带审批结果的通知不得在关联审批仍可查询前提前删除。

## 9.4 审计

安全审计日志建议保留 180 至 365 天，且不得保存原照片、备注全文、明文 Token 或完整敏感请求体。

# 10. 定时任务

| 任务 | 建议频率 | 处理内容 |
|---|---|---|
| 邀请过期 | 每分钟 | active Token → expired |
| 加入申请过期 | 每小时 | pending → expired |
| 补卡审批过期 | 每分钟 | pending → expired，Record 同步 |
| 今日记录锁定 | 每日 00:00 后 | 前一日 active → locked |
| 日终成员快照 | 每日 00:05 | 计算前一日共同完成 |
| 补卡通过重算 | 事件触发 | 重算目标日期快照 |
| 提醒扫描 | 每分钟 | 达到个人提醒时间的任务 |
| 媒体孤儿清理 | 每小时 | 清理无引用媒体 |
| 模块永久删除 | 每小时 | 回收期到期内容清理 |
| 回忆卡失效 | 事件触发 | 当月数据变化后更新 data_version |
| Outbox 发布 | 秒级轮询 | 可靠发布异步事件 |

# 11. 数据安全

- Token 仅存哈希；
- 对象存储使用私有桶；
- URL 使用短期签名；
- 备注字段加密可作为增强项；
- 日志不得打印原图 URL、Token、OpenID 全文和备注全文；
- 权限以 `module_member.status=active` 为核心校验；
- 退出成员内容由 API 层强制匿名；
- 永久删除必须覆盖数据库、缓存、搜索索引、对象存储和派生文件；
- 数据导出图不得包含完整备注和内部审批信息。

## 1. 总结：下一步不应继续堆功能

当前项目不是“功能没做完”的原型，而是“核心功能已达到 RC，但版本治理、发布治理和生产证据不足”的系统。下一步的主线应当是：

```text
冻结功能范围
→ 建立可追溯源码基线
→ 修复干净环境复现与依赖安全问题
→ 固化三套发布单元和云端配置
→ 建立 staging、备份和回滚能力
→ 完成真实端到端验收
→ 建立指标与告警
→ 再做性能、契约和代码拆分
```

在 P0 上线门禁关闭之前，不建议投入发现流、公开社区、视频、多图、会员、年度报告等新功能，也不建议先进行大规模框架迁移或数据库大版本升级。

### 1.1 推荐投入预期

以下为单名熟悉 Node.js、微信小程序和腾讯云的工程师的粗略工作量，不包含账号审批、微信审核和等待外部回调的自然时间：

| 目标 | 预计投入 | 结果 |
| --- | ---: | --- |
| 关闭发布阻断项 | 7-12 人日 | 可追溯、可构建、可回滚、无高危依赖 |
| 达到稳定运营基线 | 追加 10-15 人日 | 有 staging、真实验收、备份恢复、监控告警和限流 |
| 提升可维护性与容量 | 追加 10-20 人日 | 契约、集成测试、包体优化、代码拆分和容量模型 |

原交接报告中的 6-10 天路线可作为“最小安全闭环”，但如果要真正达到多人协作和稳定运营标准，还必须补上本报告新增发现的干净安装、包体、配置模板、鉴权边界和任务退出问题。

## 3. 优先级和里程碑

### 3.1 优先级定义

| 优先级 | 含义 | 执行规则 |
| --- | --- | --- |
| P0 | 阻止可信正式发布或可能造成安全/数据事故 | 未关闭前不新增正式用户，不扩产品范围 |
| P1 | 稳定运营、团队协作和性能基线 | P0 后立即进入，至少完成监控、测试和包体三个方向 |
| P2 | 中长期可维护性、成本和扩展性 | 依据真实业务量和指标排期，不提前复杂化架构 |

### 3.2 推荐里程碑

| 里程碑 | 建议周期 | 必须完成 | 退出条件 |
| --- | --- | --- | --- |
| M0：冻结与取证 | 第 1 天 | P0-01、P0-02、P0-03 | 源码、线上版本、配置和产物都有可核对基线 |

| M4：维护与产品数据 | 持续 | P1-08 以后和 P2 | 重构由测试保护，决策由指标驱动 |

## 9. 现在明确不要做的事情

1. 不要在没有云端版本取证前，把当前本地源码直接声明为“线上最新版”。
2. 不要把 `release/` 的最新文件名当作线上版本证明。
3. 不要在未决定 LFS/归档策略前执行“全目录 Git add”。
4. 不要直接运行自动依赖强制修复并部署 COS 云函数；必须先有事件测试和 staging 回归。
5. 不要删除 pending-record-first 兼容接口，除非确认线上最低客户端版本已经越过兼容窗口。
6. 不要先拆分独立 Worker、引入 Redis/Kafka 或升级 MySQL；先补指标、压测和恢复能力。
7. 不要继续用生产环境 ID 作为所有开发和 staging 构建的默认值。
8. 不要把本地 78 项测试通过等同于真实 MySQL、Docker、微信、COS 和真机已经通过。
9. 不要为了降低包体直接删除候选资源而不做 Mock 模式和 14 页面视觉回归。
10. 不要在 P0 未关闭时扩展公开社区、视频、多图和付费范围。

## 11. 最终建议

项目下一步最有价值的投入顺序不是继续修改页面，而是：

```text
第一优先：P0-01 + P0-02 + P0-03
  先建立可信源码、干净复现和线上真相

第二优先：P0-04 + P0-05 + P0-06 + P0-07
  再建立安全、隔离、可重复、可回滚的发布链

第三优先：P0-08 + P0-09 + P0-10
  用真实环境证据、鉴权验证和告警证明系统可运营

第四优先：P1-02 + P1-03 + P1-04 + P1-05 + P1-06
  再做测试、包体、契约、性能和任务架构收敛
```

其中最适合立即开始、且一天内能显著提升项目质量的三件事是：

1. 在初始化 Git 前修正忽略规则并决定大文件/历史发布包策略；
2. 修复根 Vitest 跨目录扫描，证明干净环境可以复现；
3. 完成云端版本和配置取证，冻结一个可追溯的 release 基线。

这三项完成后，再修复 COS 云函数依赖并搭建统一发布链，后续工作才不会继续建立在不可追溯的本地状态上。
